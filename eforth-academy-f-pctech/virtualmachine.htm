CHAPTER 1.   F-PC VIRTUAL FORTH MACHINE

 

 

 

 

 

1.1.   FORTH ON A SEGMENTED ARCHITECTURE

 

 

Nowadays people think that segmented architecture was Intel's greatest sin against humanity and that IBM's adopting this architecture for its PC series of computers set the computer industry back by 10 years.  However, looking back to the time when this architecture was first developed for the 8088 in the middle of 1970's, it was a real breakthrough against the tight grip of the 64K byte limit on the addressing space.

 

The segmented architecture was adopted by Intel long before the 8088 was even designed.  The Macro Assembler developed for the Intel Microprocessor Development Systems (MDS) had the assembler directives CODE SEGMENT, DATA SEGMENT, and STACK SEGMENT to separate assembler modules so that data and code would not be mixed.  The 8088 was designed to reduce this software concept to silicon.  Standing at the threshold between 8 bit and 16 bit microprocessor designs, it was understandable why IBM picked the 8088 as the backbone of its new PC lines, which it shoved down our throats and practically wiped out all other microprocessors except the 68000 family.

 

As far as Forth is concerned, segmented architecture is no vice.  There is no problem in making full use of all the resources provided by the CPU.  F83 did not take advantage of the segmented architecture of 8088, nor the 32 bit addressing space of 68000.  It was derived from the 8 bit figForth model, and tried to be compatible among the three implementations for 8080, 8088/86, and 68000.  The primary concerns of the F83 implementers were portability and compatibility across the different CPU's, and it was thus restricted to a 16 bit Forth.

 

The primary concerns of F-PC are performance and addressibility of the entire  memory space in the 8088 architecture.  It started with F83/8086 Version 2.1.0, which is explained fully in "Inside F83" by the author, available from Offete Enterprises.  All words needed by the interpreter and compiler have been recoded in assembly.  The dictionary has been carefully partitioned into a code segment, a head segment, and a list segment.  The list segment has been designed so that it occupies more space than a single 64K byte segment.  The result is a highly specialized Forth optimized for the 8088 segmented architecture under the MS-DOS operating system.

 

 

1.2.   THE F-PC MEMORY MAP

 

 

In this section, we shall explore the partitioned segment structure of F-PC and how the Forth machine is built upon the 8088 architecture.  Figure 1 shows an overview of the memory map of F-PC in the 640K byte space provided by a PC/XT/AT system. 

 

At the bottom of the memory map, the DOS occupies an area to provide the basic services like directory listing, file copying, loading and executing application programs.  F-PC is loaded above the DOS area.  The first part of F-PC is the Code Segment of 64K bytes.  It contains all the low level executable code, constants, variables and other data structures, including the data and return stacks, terminal input buffer and other temporary data storage areas.  Most of the Forth words deal with data stored in this segment because the CS, DS and SS segment registers are all pointing to the beginning of this Code Segment.

The variable XSEG stores the base segment address pointing to the beginning of the List Segment.  Lists in the List Segment are addressed by their segment offset relative to XSEG.  Using the segment offset instead of address offset to address lists makes it possible to address a list space greater than 64K bytes.  The trade-off is that there are bytes wasted at the end of a list before the next list starts at the next page boundary.  However, the wasted memory only accounts for about 5 percent increase in the total sized of F-PC.

 

The third segment is the Head Segment; it is next above the List Segment.  It contains the headers or heads of all the words defined in F-PC.  The headers are linked into vocabularies and vocabularies are hashed into threads.  This linked structure of headers allows F-PC to be executed and compiled very fast.  The number of threads used in a vocabulary is specified by the constant #TTHREADS during metacompilation.  Currently, a vocabulary is hashed into 64 threads with a special hashing algorithm which distributes words evenly among the 64 threads to optimize the compilation of source files.

 

The Code and List Segments are absolutely required for F-PC to run.  In a turnkey application the Head Segment can be stripped to conserve memory space.  To support user interaction, the Head Segment is necessary so that dictionary and vocabularies can be searched.  For program development, the editor in F-PC requires additional space for text manipulation.  The Text Buffer occupies another 64K segment.  It is allocated only when the editor is invoked to edit a file.  To help managing text, the editor also allocates space for a Line List Buffer, a Delete Buffer, and a Restore Display Buffer.

 

Space above the editor buffers is managed by DOS.  If an application needs more data storage space, the user can obtain more memory from DOS using DOS service request 48H.  Thus the user can access the entire 640K bytes of memory in a PC/XT/AT system.

 

 

1.3.   THE VIRTUAL FORTH MACHINE

 

 

Forth is a computer model which uses two stacks for subroutine nesting, and executes a set of instructions which are represented by addresses.  The execution addresses are generally arranged as lists.  Lists are again represented by addresses which can be used to build more powerful lists.  In Forth, the execution addresses or instructions are given English-like names which are called words.  A Forth system provides a basic set of words.  The user can define new words using the existing words.  The word set is extended until it encompasses the whole application.  Programming in Forth is thus conceptually different from programming in other conventional languages.  In Forth, you do not write programs.  Instead, you design an instruction set which becomes the solution to your problem or your application.

 

This model of a computer consists of a set of registers, a dictionary which contains all the words and their execution procedures, and additional memory to host two stacks and other necessary buffers.  Any actual computer can be programmed so that it supports the Forth model.  Thus a real computer is turned into a 'Virtual Forth Machine' which executes a Forth instruction set.  To host a virtual Forth machine, many of the registers in the 8088/86 are dedicated to functions required by the Forth model.  The projection of Forth registers on the 8088/86 CPU is shown in Table 1.

 

The 8088/86 definitely is not the ideal CPU to host a virtual Forth machine.  BP is not a real stack pointer and it is awkward to manipulate data on the return stack.  All the registers in the 8088 have some specialized characteristics which makes coding any application a real challenge.  Nevertheless, F-PC is coded to make the best use of all the registers in the 8088 and squeezes the last ounce of performance out of this CPU.

At the assembly-language level, data are stored on the data stack by the PUSH instruction, and are popped back into internal registers for manipulation by POP.  Addresses or data on the return stack can be moved to/from the internal registers by MOV instruction using BP relative mode to specify items on the return stack.  The ES:SI register pair is the Instruction Pointer (IP), which is used to point to an address where the execution address of the next word to be executed is stored.  The self incrementing string instruction LODSW ES: is thus very useful in processing a list of execution (code field) addresses stored in the List Segment. 

 

As the LODSW instruction reads the execution address into the AX register, a JMP AX instruction causes the referred word to be executed.  An interesting consequence is that the AX register always points to the beginning of a code field when a Forth word is executed.  Hence the AX register becomes the Current Word or W register in the virtual Forth machine, very naturally.  If a Forth word has to access data stored in its Body or Parameter Field, the address of Body can be computed by adding 3 to AX.  If the Forth word does not refer to its code field or its Body, AX can be used freely as a scratch pad register.  In fact, most Forth code words uses AX as the first choice of scratch pad.  The second choice of scratch pad register is DX.  Special code ending words are defined to push AX or AX and DX on the data stack before executing the next Forth word.

 

Since the ES register is used to address the colon definitions in the List Segment, and the CS, DS, and SS registers have to point to the Code Segment, these four segment registers cannot be disturbed.  If any of these registers are needed to perform some special functions like string compare and string move, their contents must be saved and restored before executing NEXT at the end of a Forth code word.

 

All system variables in F-PC are saved in a area at the top of the Code Segment.  The beginning of this area is pointed to by the address contained in a variable UP.  These variables are addressed by an address offset relative to the address in UP.  This is not significant in a single task environment but is very important when you create background tasks in F-PC.  Each task has its own user area and it keeps a unique copy of all user variables.  The user area thus preserves the entire environment of a task, allowing tasks to be switched conveniently and very fast.  It also allows Forth words to be re-entrant, so that the same code can be shared among all the tasks.

 

 

1.4.   THE CODE AND PARAMETER FIELDS

 

 

The Code Segment of F-PC looks very similar to the entire F83 system.  It contains a dictionary at the bottom.  The return stack and the terminal input buffer are on the top.  The free memory space between the top of the dictionary and the bottom of the return stack is shared by the data stack and the dictionary extension when new words are added to the dictionary.

 

In the dictionary, each Forth word occupies a variable length field call the Code Field.  The address of the first byte in this field is called the Code Field Address (cfa) or Execution Address of this word.  All Forth words are referenced by their Code Field Addresses.  The Code Field contains executable machine code.  A Forth word is executed by directly jumping to its Code Field.  In Forth terminology, this arrangement is called 'Direct Threaded Code.'  This is different from the more conventional 'Indirect Threaded Code' used by F83 and many other existing Forth systems in which the code field contains an address of executable code rather than the code itself.  Direct Threaded Code is much faster than Indirect Threaded Code Because it eliminates a level of indirect jump.

In a low level code word, the Code Field contains machine code and is terminated by the NEXT instructions (LODSW ES:  JMP AX), or a JMP >NEXT instruction, which allows the next Forth word to be executed.  In other types of Forth words, the Code Field begins with a JMP or CALL instruction which invokes the inner interpreter specified for this type of words.  Three bytes from the beginning of the Code Field, after the JMP or CALL instruction, is the Body or Parameter Field of the word.  The Parameter Field contains data or other information needed by the word to perform its function.  Figure 2 shows a collection of code and parameter fields for various types of Forth words, like constants, variables, colon definitions, arrays, etc.

 

In an indirect threaded Forth system, the Code Field is two bytes long and contains a pointer to a piece of executable code which is the inner interpreter for this type of words.  The Parameter Field follows immediately after the Code Field.  In a code word, the pointer in the Code Field points to its Parameter Field, which contains the executable code.  The indirect jump to the code in the Parameter Field via the Code Field wastes a considerable number of machine cycles.  The direct threaded code in F-PC gains much of its speed by eliminating this indirect jump.  The cost is a three byte code field for words other than code words, one more byte per word than indirect threaded code.

 

 

1.5.   THE COLON LISTS

 

 

Colon definitions are the most prevalent type of Forth words.  In F-PC, a colon definition is compiled in three separated pieces.  The head is placed in the Head Segment; it contains a view field, a link field, a name field, and a code pointer field.  The executable part is compiled in the Code Segment, which is composed of a JMP NEST instruction and a list segment offset address.  The list part is stored in the List Segment, which is a list of code field addresses.  The physical segment address of this list is obtained by adding the contents of XSEG to the segment offset address stored in the Body (parameter field) of the colon word.

 

This rather interesting relationship among the three separated parts of a colon definition is shown in Figure 3.  The Code Pointer in the head of a colon word points to the Code Field in the Code Segment.  The Parameter Field points to the beginning of a list of code field addresses in the List Segment.  To execute a colon word, the text interpreter or the outer interpreter in F-PC searches for the name of the colon word in the Head Segment.  When the colon word is found, the execution address is obtained in the Code Pointer Field in its head. 

 

A colon word is executed by a JMP AX instruction with AX pointing to its Code Field.  The first instruction in its code field is JMP NEST, which saves ES:IP on the return stack, calculates the absolute page address of the list by adding the contents of its parameter field and the contents of XSEG, and then stores the page address in the ES register.  After that, the NEXT instruction at the end of the NEST routine obtains the first execution address from the list of code field address and starts executing the words compiled into the colon definition.

 

The code field addresses in the list of a colon definition are executed in sequence.  The last code field address in the list points to the code field of UNNEST.  UNNEST pops the top two items on the return stack back into the ES:IP register pair and thus restores the condition before entering into this colon word.   The NEXT instruction at the end of UNNEST causes the code compiled after the just-executed colon word to be executed.

 

Colon words are similar to subroutine calls in assembly code and procedures in conventional high level languages.  Colon words are much more powerful because of the simplicity in the structure of address lists, and because parameters are passed on a separate data stack.  The colon definitions can be nested with only a small overhead in nesting and un-nesting.  Colon words are referred to by their execution addresses for execution and in compilation.  They are structures more powerful and more versatile than subroutines or procedures.  They are instructions to the virtual Forth machine, just like code words constructed from machine code.

 

 

1.6.   THE HEADS

 

 

The Head or Header of a word contains its name and information about how it is to be executed, its context (vocabulary), and where its source code is.  All heads are collected in the Head Segment.  A head is a variable length structure with information arranged as shown in the upper left of Figure 3.  The first two bytes are the View Field, which contains a byte offset address in the file containing its source definition.  (The file is identified by the view field address of this word and the link field addresses of the loaded files which are linked into a file list).  The view field locates the source code of this word so that the user can quickly find the source code by the VIEW command in F-PC.  The ability to locate quickly the source code greatly improves the friendliness of F-PC.  For new users it provides on-line documentation for inspecting and studying the system.  For programmers, it gives fast access to the source code for debugging and modification.

 

The next two bytes are the Link Field, which contains an address pointing to the link field of the previous word in the same vocabulary thread.  The link fields connect words with the same hash code into threads so that they can be searched quickly to locate a word by its name.  In F-PC, the head dictionary is divided into several vocabularies.  Words in a vocabulary are hashed into 64 threads by the first two characters and the lengths of their names.  The last

After the link field is a variable length Name Field.  The first and last byte in the Name Field are flagged by setting the most significant bits in them.  The first byte is called the Length Byte because it has the character length of the word name stored in the lower 5 bit field.  Thus F-PC allows a word to have a name with up to 31 characters.  Bit 6 in the Length Byte is the Immediate Bit.  During compilation of a colon definition, words are normally compiled into a list.  When the Immediate Bit is set, the word is not compiled into the list, but instead is executed immediately. 

 

Bit 5 in the length byte is the Smudge Bit.  When the Smudge Bit is set, the Forth text interpreter will not be able to find this word.  This bit is used primarily to prevent finding words which are not compiled successfully.  When a head is created, this Smudge Bit is always set to 1.  After the colon word is compiled successfully, this bit is turned off so that the new word is revealed to the text interpreter.  However, if compilation is unsuccessful, the word remains 'smudged' and the interpreter and compiler will not be able to find it.  Thus the user is protected from compiling or executing invalid words.

 

Most Forth systems use the smudge bit to prevent invalid words from being executed or compiled.  However, the invalid words still occupy dictionary space.  F-PC does not use the smudge bit to protect the system.  Instead, it only links words successfully compiled into the dictionary.  Thus when a word is not compiled successfully, it does not take up memory space.

 

The name of a word is compiled in the Name Field.  Up to 31 characters can be included.  The last character is indicated by a 1 in bit 7, to delimit the name field.

 

The last field in a head is the Code Pointer Field, which contains the execution or code field address of this word.  The address points to the code field of this word in the Code Segment.  This address will be used to execute this word by the interpreter or compiled into a list by the colon compiler.

 

The first 256 bytes in the Head Segment are a Code Search Table.  This table reduces the time to search the Code Pointer Fields in the heads by the decompiler.  The vocabulary/thread structure is designed to locate the code field of a word from its name.  The decompiler needs to do the search in reverse, finding the name of a word from its code field address.  Because F-PC moves the heads out of the code dictionary and puts them in the Head Segment, the natural link between a code field and its name field is broken.  To find the name field from a code field address, one would have to search all heads in the Head Segment.  This search would be very time consuming.

 

To reduce the amount of searching, we divide the Code Segment into 64 1K byte regions.  Each region has four bytes in the Code Search table.  These four bytes define the area of heads to be searched for a code whose code field address falls into this code region.  The first two bytes are the lower bound of the head space to be searched, and the last two bytes are the upper bound.  Therefore, to search the name of a code, we have to identify its code region and then fetch the upper and lower bounds of the head space.  Only the heads between these bounds have to be searched.

 

The Code Search Table is updated by the compiler when a new word is added to the dictionary.

We will follow the building process of the F-PC kernel according to the sequence of events coded in the KERNEL1.SEQ file.  Since most Forth words have names in the upper case, you should be able to distinguish the code from the narration, which is in lower case.  Code is shown in the vertical style on the left hand side of a page.  In-line comment is shown on the right hand side, following a back slash \ which is also used in F-PC to start a comment which extends till the end of line.

 

It is difficult to follow and fully understand this part of the F-PC kernel because the loading is controlled by the F-PC metacompiler.  Some of the words are compiled into the target dictionary as expected, but some words are compiled into the host dictionary as tools to aid the target compilation.  Some knowledge about the F83 or F-PC metacompilers would be very useful.  However, you will gain some insight into the inner structure of a virtual Forth machine with only elementary familiarity with Forth in general by casually going through this section.  When you encounter problems about the inner interpreters later, you can always come back and pick up the details then.

 

The original design of this book was to include the F-PC metacompiler to achieve a system closure.  As things stand now, the metacompiler and many other utilities will be published in separate volumes.  In the mean time, you can use Chapter 25 in "Inside F83" for information about the metacompiler in F83, which is very close to the F-PC metacompiler.

 

The basic problem in understanding F-PC, or F83 and many other Forth systems in general, is that there is no starting point.  The Forth is generated by itself with metacompilation.  You cannot fully understand Forth not knowing the metacompiler.  You cannot understand the metacompiler not knowing the Forth under it.  Chicken or egg, which comes first?

 

The best place to start is really not here at the beginning.  For those who are anxious to learn about assembly programming and Forth, Chapter 2 is the proper place to start.  There you will find the definitions of the most useful Forth words and you can build up you knowledge of Forth from there. 

 

The remaining of this section discusses the inner interpreters which are code that executes Forth instructions using the resources provided by the host CPU.  The information about the inner interpreters is not necessary in order to use Forth.  However, if you have to do special things and have to tinker the 8088 CPU and the virtual Forth machine, you need to dig through this section to find out why things are done the way the are, and how to tailor the system for your needs.

We define a few macros here to make our life a little easier later.  Using NEXT as a macro allows us to put it in-line later.

 

>NEXT is where all the action is.  It is the guts of the Virtual Forth Machine.  It must advance the interpretive pointer held in the ES:IP register pair and jump indirect through AX to what it points to.

 

>NEXT   The centralized return point of all code words in F-PC when NEXT is not compiled in-line.  This is known as THE Inner Interpreter of Forth.  As a colon word is executed, the Forth machine scans through a list of code field addresses in the list space.  ES:IP is pointing to the next code field address in this list.  LODSW ES: fetches this address into the AX register and increments IP so that ES:IP points to the next code field address to be executed.  JMP AX executes the code stored in the code segment starting at the address pointed to by AX register.  This code sequence causes the next Forth word pointed by ES:IP to be executed.  The Forth machine runs on this way indefinitely or until F-PC is terminated.

 

The DPUSH and APUSH labels are space savers.  We jump to them in many code words when we want to push their contents on the data stack. 

 

APUSH   Push contents of AX on the data stack and then execute NEXT.  AX generally holds the most immediate results to be returned to the data stack by a code word.

 

DPUSH   Push contents of DX on the data stack and fall into APUSH.  DX is used to hold the second piece of data to be returned on the data stack.

    MOV AX, # ABNORM >NEXT - 3 -    \ Offset from >NEXT to  ABNORM

    MOV CS: >NEXT 1+ AX     \ Complete the JMP code

    POP AX

    IRET

    END-CODE

 

DOSBK   Call DOS keyboard service 16.  The function number n must be on the data stack.

 

LABEL DOSBK     ( n -- )

    PUSH AX

    MOV AH, # 0                 \ Throw away BREAK KEY

    INT 16

    POP AX

    CLC

    RETF

    END-CODE

DECIMAL

 

NEST        The run-time code (the inner interpreter) for colon words .  It pushes the current ES:IP register pair onto the return stack and sets the ES:IP to point to the beginning of a list of words to be executed.  It allows high level words to call other high level words with almost unlimited nesting.  In the code field of a colon definition, the first three bytes contain JMP NEST instruction.  The next byte contains a relative segment address, pointing to the list of code field addresses compiled in the list space, offset by the contents of XSEG.

 

LABEL NEST

    XCHG RP, SP         \  4 cycles. Use SP to address return stack.

    PUSH ES         \ 10 cycles. Save ES.

    PUSH IP         \ 11 cycles. Save IP.

    XCHG RP, SP         \  4 cycles. Restore RP.

    MOV DI, AX          \  2 cycles. Code field address

    MOV AX, 3 [DI]      \ 18 cycles. Get to BODY of code and fetch relative segment

 

LABEL NESTPATCH         \ This location is later patched at boot time to correct for the

    ADD AX, # XSEG      \ actual value of XSEG at boot time.

    MOV ES, AX          \  2 cycles. Move it into ES

    SUB IP, IP              \  3 cycles. Clear IP

    NEXT                \ Ready to process list

    END-CODE

META

 

EXIT        Pop an ES:IP pair off the return stack and place it in the ES and IP register pair to resume processing the unfinished list of code field addresses.  Terminate a high level definition by nullifying what NEST had wrought. 

CODE EXIT   ( -- )

    XCHG RP, SP         \  4 cycles. Use SP as RP.

    POP IP              \  8 cycles. Restore IP

    POP ES          \  8 cycles. Restore ES

    XCHG RP, SP         \  4 cycles. Restore RP

    NEXT

    END-CODE

 

?EXIT   Exit from a definition if the flag on stack is true.

 

CODE ?EXIT  ( f1 -- ) 

    POP CX

    CX<>0 IF

        JMP ' EXIT

    THEN

    NEXT

    END-CODE

 

UNNEST  Same as EXIT.  Compiled by ; .  The alias is defined to help the decompiler to recover ; .

 

DODOES  The inner interpreter of the defining words.  The first three bytes in the code field of a daughter word created by a defining word are CALL DODOES, which calls the high level interpreter specified after DOES> in the defining word.   First it pushes the ES:IP pair onto the return stack and then it pushes the BODY address of the word being executed onto the data stack which is what the CPU thinks of as its return stack.

 

LABEL DODOES    ( addr1 addr2 -- addr1 )    \ addr1/2 are from two previous calls.

    XCHG RP, SP

    PUSH ES

    PUSH IP

    XCHG RP, SP

    POP DI          \ Pop the BODY address

    MOV AX, 0 [DI]      \ Get the list offset

 

LABEL DOESPATCH         \ This location is later patched at boot time to correct for the

    ADD AX, # XSEG      \ actual value of XSEG at boot time.

    MOV ES, AX          \ Move to ES

    SUB IP, IP          \ Clear IP

    NEXT                \ Execute high level inner

    END-CODE            \   interpreter.

EXEC:   Select the n'th execution address in the following address table and execute it.  This is a very fast and very powerful case structure compiled in the List Segment.  It is similar to CASE: in F83.  It is used in KEYTABLE, p. 91.

 

CODE EXEC:  ( n -- )

    POP BX          \ Pop the case number

    SHL BX, # 1         \ Make it an address offset

    ADD IP, BX          \ Point it into the address table

    LODSW ES:           \ Get execution address

    XCHG RP, SP

    POP IP              \ Pop ES:IP

    POP ES          \ Prepare to leave current colon word

    XCHG RP, SP        

    JMP AX          \ Execute and exit

    END-CODE

 

DOUSER-DEFER    The run-time code for user deferred words.  They are identical to regular deferred words except that each task has its own version.

 

LABEL DOUSER-DEFER

    POP BX          \ BODY address

    MOV BX, 0 [BX]      \ User variable offset

    ADD BX, UP          \ Address in user area

    MOV AX, 0 [BX]      \ Fetch execution address

    JMP AX          \ Do it

    END-CODE
